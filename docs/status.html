SCRATCH-E2E — what it does, and what is left

Eight standalone pipelines merged into one DAG, with a compartment split, a publication figure system, per-stage smart reports and an offline interpretation agent. The engineering is done and verified. The science is not — nothing has yet run on real data. That distinction is what this page is for.

How to read the status column

Levels of evidence

Every claim below is tagged with how it was checked. These are not equivalent, and conflating them is how a pipeline gets called "working" when it has never seen a cell.

Level 0 Written Code exists. Nothing has executed it.
Level 1 Stub-verified The DAG runs end to end. Channels, joins, gating and config are correct. No computation happened.
Level 2 Executed Real R / JS / Quarto ran and the output was inspected. True of the figure system, reports and agent.
Level 3 Scientifically validated Run on your data, results checked by a person who knows the biology. Nothing has reached this.

The honest position

What "done" does and does not mean

✗ Nothing in this pipeline has processed a real cell.

Every analysis claim is Level 1: the DAG is correct, the channels join, the config resolves, the stubs pass. That is a real and necessary result — it is what makes a first real run debuggable rather than a guessing game — but it is not evidence that the biology is right. The first run on your data is a shakedown, and should be treated as one: one cohort, inspected stage by stage.

What to do next

Ranked by what actually unblocks progress

Ordering is deliberate: nothing below #1 is worth much until #1 has happened, because a real run is what turns Level 1 into evidence — and it is also what will expose the problems no amount of stub-running can.

1First real run — one cohort, to the compartment splitdays · shakedown

--to stratify on one GBM or ovarian cohort. Stop there and inspect: does the CNV evidence separate, does the lineage gate override a sensible number of cells, is the false-positive rate credible?

This is the only step that converts the whole build from "wired" to "working". Everything else is speculation until it runs.

2Compositional analysis done correctly~1 day

Cell-type proportions sum to one, so a tumour compartment expanding mechanically shrinks every other population. The TME stage currently tests per-sample proportions with a rank-sum test, which will report spurious "myeloid depletion".

A correctness bug in analysis you are already running — not a new feature. scCODA or a Dirichlet-multinomial model fixes it.

3Biological findings per stage~1 day per 3 stages

Each stage emits its own findings.json: "subclone 3 is confined to patient 04", "metaprogram 7 recurs in 9 of 12 samples". Inherited automatically by the stage report and the agent.

This is what turns the reports from competent to genuinely useful — and it is what gives the agent something worth asking about.

4Metaprogram × CNV subclone linkage~1 day

Both per-cell inputs already exist and are joined in the master object; nothing yet tests whether a programme is clone-intrinsic (genetically driven) or plastic (shared across clones).

Usually the biological headline in this kind of study, and the data is already there.

5Notebook editorial pass~2 days

Convert the 4 remaining stacking loops to filtered views, add verdict/tiles to the major reports, and give each figure a lede. 2 of 40 notebooks use the components today.

Mechanical for QC-like stages; genuinely editorial for CNV, metaprograms and TCR, where deciding the headline is the work.

6Validate the NMF engines against each otherhours

--metaprog_nmf_engine both on one cohort, then read the concordance off the Jaccard heatmap PostNMF already produces.

Python is the default on a structural argument. Confirm it before it drives a publication.

7TCR clonotype × phenotype transition~1 day

Clonotypes and pseudotime are already joined, but only a Spearman correlation is computed. Proper clonal-transition analysis — which phenotypic states share clonotypes — is the standard readout.

Uses data already being produced; currently under-analysed.

8Cell-communication differential testing~half day

LIANA and CellChat describe interactions; nothing compares them between conditions. CellChat's own differential analysis answers "which signalling changes in Case vs Control".

A descriptive stage becomes a comparative one.

9Local model + CI~1 day

Point the agent at an Ollama endpoint on the HPC node and confirm the phrasing layer. Add a CI job running the stub DAG on every change.

The stub suite already exists and catches real breakage — it should run automatically.

Rewriting the vendored science 40 of 41 notebooks have no analysis logic changed. 26 carry only the injected figure-system chunk (+16 / −0 lines); the rest are presentation only — raster DPI raised to 400, two viridis_d scales swapped for the validated categorical palette, one figure stack turned into tabs, and one missing results: asis fixed.

The single exception is Metaprog_PostNMF.qmd, which had to learn to read the Python engine's basis matrices.

The reason is not caution for its own sake: these notebooks cannot be executed here, so any edit to them is unverifiable, and the failure mode is a run that completes with subtly wrong numbers. That risk is real — a two-line colour swap in GLIPH2 left an option = "turbo" argument on a scale that has no such formal, which would have crashed the render; it was caught only by inspecting the substituted lines.

Hence STAGE_REPORT reads each stage's published outputs rather than living inside its notebook. The cost: reports see only what a stage writes to disk, which is exactly why findings are structural rather than biological. A test dataset and working containers would invert this trade — edits become verifiable, and going inside the notebooks becomes the better option.
